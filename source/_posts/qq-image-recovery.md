这次实验用 Wireshark 抓取自己的 QQ 通信流量，判断图片传输使用的协议，再用 010 Editor 从抓到的数据中提取图片。

实验过程中遇到的一个问题是，已经找到了图片下载连接，导出的文件却还带着 HTTP 响应头。找到图片真正的起点、去掉前面的协议数据后，图片才恢复出来。

<!-- more -->

## 一、实验工具与分析范围

本次使用的工具是 Wireshark 和 010 Editor。Wireshark 用来查看报文、追踪 TCP 流，010 Editor 用来检查十六进制数据并提取图片。

前一天讨论文字消息抓包时，首先需要解决的是怎样从整台电脑的网络流量中定位 QQ。可以借助 Windows 资源监视器查看 QQ 的网络活动，再结合远程地址、端口和发送消息的时间缩小范围。

文字消息和图片传输需要分别验证。本文主要记录已经恢复成功的这次图片传输，文字消息的协议判断还需要对应的抓包证据。

## 二、从 HTTP 请求定位图片传输

打开抓包文件后，先通过 IP 地址筛选相关流量。筛选表达式可以写成下面这样，将示例地址换成实验中的实际地址。

```text
ip.addr == 192.0.2.1
```

筛选后，可以看到一条 HTTP GET 请求，请求路径以 `/qqline/` 开头。它前面还有 TCP 建立连接的报文。

![图 1　IP 筛选后的报文列表，包含 TCP 握手与 HTTP GET 请求](/images/qq-image-recovery/01-http-request.png)

截图中的第 29、31、32 号报文依次带有 `SYN`、`SYN, ACK` 和 `ACK` 标志，能够看到 TCP 三次握手的过程。第 33 号报文随后发出了 HTTP GET 请求。

这条连接中，请求方向的源端口是 `55869`，目标端口是 `8082`；响应方向则相反。

这里判断 TCP 的依据来自报文中的协议层和握手过程。单看端口号，无法确定它承载的具体业务。

## 三、检查 TCP 详情与分段数据

选中第 33 号报文，在详情区域展开 Transmission Control Protocol，可以看到对应的源端口、目标端口，以及 TCP 流编号。

本次连接的流编号是 `6`，后续可以直接使用下面的显示过滤器查看这条连接。

```text
tcp.stream eq 6
```

![图 2　GET 请求的 TCP 详情与对应的流编号](/images/qq-image-recovery/02-tcp-details.png)

GET 请求后面出现了许多由 `8082` 端口发回的 TCP 报文，其中多条带有下面的提示。

```text
TCP PDU reassembled in 921
```

这表示 Wireshark 将这些分段中的数据参与重组，并在第 921 号报文处展示相应的重组结果。因此，提取图片时需要处理重组后的数据，单独保存其中一个 TCP 报文通常得不到完整图片。

## 四、追踪 TCP 流，查看 HTTP 响应

右键选择相关报文，进入“追踪 TCP 流”，选择服务器到客户端的方向，再把显示方式切换成 ASCII。

这里的“服务器”指这条 TCP 连接中响应请求的一端，不能仅凭这个称呼认定它就是腾讯的公网服务器。

流的开头可以读到下面的内容。

```http
HTTP/1.1 200 OK
Server: QQ/1.0.0 (Tencent)
Content-Length: 1203661
Connection: keep-alive
```

![图 3　ASCII 视图中的 HTTP 响应头与后面的 PNG 数据](/images/qq-image-recovery/03-http-response.png)

`200 OK` 表明该请求返回了成功响应。`Content-Length` 给出了响应正文的长度，本次是 `1,203,661` 字节。

响应头后面还能看到 `PNG`、`IHDR` 等内容，说明接下来的数据具有 PNG 文件的特征。

ASCII 视图适合阅读 HTTP 头，图片中的二进制内容则会显示成大量不可读字符。这种显示现象本身不能作为加密的依据。

为了在 010 Editor 中继续处理，应当将对应方向的数据按“原始数据”保存。ASCII 视图用于观察，复制窗口中的文字不能代替保存原始二进制字节。

## 五、在 010 Editor 中找到图片文件头

用 010 Editor 打开导出的数据，可以看到文件开头仍然是 HTTP 响应。

```text
48 54 54 50 2F 31 2E 31 20 32 30 30 20 4F 4B
```

它对应的文本是 `HTTP/1.1 200 OK`。这部分属于 HTTP 协议数据，图片内容还在后面。

在 010 Editor 的查找栏选择 Hex Bytes，搜索 PNG 文件签名。

```text
89 50 4E 47 0D 0A 1A 0A
```

PNG 文件的前八个字节应当是这一序列，后面再按规定组织数据块。[PNG 文件格式规范](https://www.w3.org/TR/png/#5PNG-file-signature)

![图 4　010 Editor 中尚未删除 HTTP 头的数据，PNG 签名位于偏移 0x62](/images/qq-image-recovery/04-png-offset.png)

截图中，搜索栏输入的是 `89504e`。这三个字节可以帮助找到候选位置，找到后还要继续核对完整的八字节签名。

本次 PNG 文件头位于偏移 `0x62`，也就是十进制的 `98`。

观察文件头前面的字节，还能看到 HTTP 响应头结束时的空行分隔符。

```text
0D 0A 0D 0A
```

紧接着就是 PNG 文件签名。两者的位置相互吻合，说明这次响应的图片正文从偏移 `0x62` 开始。

## 六、去掉 HTTP 响应头，保留图片正文

定位图片起点后，需要去掉偏移 `0x00` 到 `0x61` 的数据，总共 98 字节，保留从 `0x62` 开始的图片正文。

处理时应当删除前面的字节，或把正文复制到新文件。用零覆盖原来的响应头，会让图片签名继续停留在原来的偏移，文件起点仍然不正确。

![图 5　提取后的图片正文从偏移 0x00 开始就是 PNG 签名](/images/qq-image-recovery/05-png-extracted.png)

处理后的文件从偏移 `0x00` 开始就是 PNG 签名，后面能看到 `IHDR`。

这次还可以用文件大小检查提取范围。

```text
处理前文件大小    1,203,759 字节
HTTP 响应头长度          98 字节
处理后文件大小    1,203,661 字节

1,203,759 - 98 = 1,203,661
```

处理后的大小恰好等于 HTTP 响应头中的 `Content-Length`。这为正文提取范围正确提供了进一步证据。

98 字节只是本次响应头的长度。其他连接的响应头可能包含不同字段，不能在下一次实验中直接照搬这个删除长度。

## 七、打开恢复的图片

保存处理后的文件，再用图片查看器打开，可以正常显示图片。

![图 6　恢复后的图片在查看器中正常显示，尺寸为 1206 × 2622](/images/qq-image-recovery/06-recovered-image.png)

本次操作中使用过 `4.jpg`、`5.jpg` 这样的文件名，但从文件头可以确定，提取出的图片实际采用 PNG 格式。整理实验文件时，应当把最终文件命名为 `.png`。

修改扩展名不会转换文件格式。有些图片查看器能够根据文件内容识别 PNG，因此即使扩展名写成 `.jpg`，仍然能够打开。

恢复后，查看器显示图片尺寸为 `1206 × 2622`。010 Editor 中 `IHDR` 后面的宽高字段也能对应上这两个数值。

```text
00 00 04 B6    宽度 1206
00 00 0A 3E    高度 2622
```

文件头、正文长度和打开后的尺寸能够互相对应，说明这次提取得到了一份能够正常解码的 PNG 图片。若要进一步证明它与发送前的原文件逐字节相同，还需要比较两份文件的哈希值。

## 八、本次实验能说明什么

这次图片下载通过 HTTP/1.1 传输，底层使用 TCP。抓包中能够看到明文 HTTP 响应，也能够直接提取 PNG 文件并打开，因此在本次抓包位置观察到的这段图片下载流量中，图片内容没有受到 TLS 或额外应用层加密的保护。

这个结论只适用于本次图片下载。QQ 的文字消息、图片上传，以及其他网络环境下的传输方式，都需要分别抓包验证。

发布实验截图时，还应遮住下载请求里的完整路径和 token。只给 IP 地址打码，仍然可能留下访问凭据。图片中附带的 EXIF、XMP 等元数据，也应检查是否包含不适合公开的信息。本文前两张截图已增加不透明遮挡，其余实验数据与图片保持原样。
